# Live Command Center Design

## Purpose

Make live background games feel better than a generic GM sim by combining three things competitors usually split apart:

- a visual game board that looks sport-native
- a readable feed that explains why events happened
- GM context from rotations, coaching styles, scouting history, fatigue, and player identity

This should preserve the existing fairness rule: the game result is generated by the server and revealed over time. GMs should not lose because they were not staring at the phone. The upgrade is a richer live broadcast and decision context, not twitch control.

## Product Principles

1. Passive-first, agency-before-tipoff.
   GMs make rotation and coaching choices before the game starts. Live mode rewards watching, but does not require watching.

2. Explain the game, not just the score.
   Every major run, stop, mismatch, hot streak, and collapse should have a reason tied to player skills, coaching style, fatigue, or matchup context.

3. Sport-native, not NBA with different labels.
   NBA uses possessions and court spacing. NFL uses drives, down-distance, field position, and explosive plays. MLB uses innings, count, outs, base state, pitcher-batter duels, and bullpen pressure.

4. Spoiler-safe.
   The final result can exist on the server immediately, but the app should reveal it according to the stored live window.

5. Additive migration.
   Existing completed games and older timelines must still render. New fields should be optional until all generation paths are upgraded.

## Existing Foundation

The current app already has several pieces to reuse:

- `app/screens/season/live-mode.tsx` renders the live scoreboard, visual board, event feed, starter matchups, player stats, and period scoring.
- `domain/nba/liveTimeline.ts` supports timeline events, court positions, event types, lineup snapshots, and reveal timing.
- `functions/franchise/possessionTimeline.js` generates NBA possession-style events and box score deltas.
- `functions/franchise/sportSimulation.js` already separates NFL and MLB simulation output from NBA scoring.
- `functions/franchise/matchups.js` owns game request, prep, coaching plan snapshots, simulation windows, and final result writes.

The next design layer should enhance these systems instead of replacing them.

## User Experience

### Calendar

Games should clearly show four states:

- `Scheduled`: game can be requested or simulated when allowed.
- `Preparing`: both sides have a short setup window for rotations and coaching style.
- `Live`: the 15-minute reveal is active, with a visible live score and a Watch action.
- `Final`: result, box score, and recap are available.

Live cards should show a small current score and period/inning/drive marker without leaking the final score early.

### Pregame

Before launch, each side can choose:

- rotation or lineup
- coaching style
- focus player or balanced approach
- risk level
- sport-specific adjustment

Examples:

- NBA: pace and space, post centric, triangle, attack the paint, 3 point first, flop and bait, zone/man up, blitz pick and roll, protect paint
- NFL: establish run, spread tempo, play action, deep shots, bend but do not break, blitz heavy, bracket star receiver, chew clock
- MLB: aggressive baserunning, patient approach, power swing, small ball, quick bullpen hook, pitch around star, defensive shift, steal pressure

These plans are snapped at tipoff/kickoff/first pitch and stored with the game.

### Live Command Center

The live screen should have five stacked zones:

1. Scoreboard
   Shows teams, score, status, period, clock or inning, possession/base/drive context, and live/final state.

2. Visual game board
   NBA: half/full court with player tokens, shot zones, ball movement, possession arrows, and home arena colors.
   NFL: field view with line of scrimmage, first-down marker, ball spot, drive direction, personnel dots, and down-distance.
   MLB: diamond view with base runners, outs, count, pitcher-batter matchup, bullpen/stamina pressure, and batted-ball location.

3. Game feed
   A play-by-play list with short readable events. Important events can expand into a "why it happened" explanation.

4. Command insights
   Non-mutating insight cards that explain the current game:
   - matchup edge
   - hot player
   - weak link being attacked
   - fatigue warning
   - coaching style effect
   - turning point

5. Stat and story drawer
   Quick links to box score, team stats, player matchup rows, coaching impact, and postgame recap once final.

## Timeline Event Enrichment

New events should keep existing fields and add optional command-center fields:

```ts
type LiveCommandEvent = {
  id: string;
  period: number;
  clock: string;
  eventType: string;
  actingTeamId?: string;
  playerId?: string;
  playerName?: string;
  text: string;
  homeScore: number;
  awayScore: number;
  x?: number;
  y?: number;
  statDeltas?: Record<string, unknown>;
  tags?: string[];
  importance?: 0 | 1 | 2 | 3;
  spotlight?: "score" | "stop" | "turnover" | "injury" | "clutch" | "run" | "substitution" | "manager";
  why?: string;
  pressure?: "low" | "medium" | "high" | "clutch";
  coachContext?: string;
  matchupContext?: string;
  winProbability?: {
    home: number;
    away: number;
  };
  visual?: {
    sport: "nba" | "madden" | "mlb";
    possessionTeamId?: string;
    ball?: { x: number; y: number };
    players?: Array<{ id: string; teamId: string; x: number; y: number; label?: string }>;
    football?: {
      yardLine: number;
      down: number;
      distance: number;
      driveDirection: "left" | "right";
      firstDownYardLine?: number;
    };
    baseball?: {
      balls: number;
      strikes: number;
      outs: number;
      bases: { first: boolean; second: boolean; third: boolean };
      battedBall?: "grounder" | "liner" | "fly" | "popup" | "home_run";
    };
  };
};
```

All fields after the existing base event shape are optional so old timelines keep working.

## Coach Windows

The first version should not allow midgame outcome-changing buttons. Instead, "Coach Window" cards should explain how the locked plan is affecting the game.

Examples:

- "3 Point First is creating early looks, but the opponent is winning long rebounds."
- "Blitz Pressure forced two rushed throws, but left the middle open on third down."
- "Quick Hook saved the starter from damage, but the bullpen is already thin."

Later, if live adjustments are added, they must follow strict fairness rules:

- both teams receive the same adjustment windows
- windows are tied to game clock, not user presence
- missed windows resolve to the pregame plan
- effect sizes stay small and transparent
- solo games can let the user choose against CPU only if commissioner settings allow it

## Sport-Specific Views

### NBA

Build on the possession timeline:

- court movement from actual possession events
- lineup-aware tokens
- shot zone and rebound path hints
- foul trouble, runs, hot hand, and matchup attack tags
- starter matchup rows stay visible above or beside the feed
- coaching context from first-half and second-half presets

The NBA view should feel like a tactical broadcast, not an arcade court.

### NFL

The NFL view should center on drives:

- field position
- down and distance
- quarter and clock
- possession direction
- drive summary card
- explosive play markers
- red-zone pressure
- turnover danger
- play-caller identity from coaching style

The feed should group events by drive so users can understand field-position swings.

### MLB

The MLB view should center on pitcher-batter tension:

- inning and half-inning
- outs
- count
- base state
- pitcher stamina
- batter handedness or archetype when available
- bullpen readiness
- batted-ball result and runner advancement

The feed should group events by plate appearance and inning.

## Postgame Story

Every live game should end with a short recap generated from structured game facts:

- final score
- turning point
- best player
- hidden hero
- coaching impact
- stat that decided the game
- injury or fatigue note when relevant
- what the result means for standings, streaks, playoff race, or rivalry history

The recap should be stored with the game so the result screen, scouting history, notifications, and team pages all tell the same story.

## Notifications

Notifications should be meaningful and not spammy.

Required notification types:

- matchup request received
- matchup accepted and prep window started
- live game started
- game entering clutch window
- final result available

Optional later notification types:

- upset alert
- overtime or extra innings
- player record watch
- injury update
- rivalry result

Notification copy must remain spoiler-safe unless the game is final.

## Data Model

Scheduled game document additions:

```ts
type LiveCommandState = {
  liveTimelineVersion?: number;
  simulationStartedAtMs?: number;
  simulationEndsAtMs?: number;
  revealDurationMs?: number;
  commandCenterVersion?: number;
  coachWindows?: Array<{
    id: string;
    period: number;
    clock: string;
    teamId: string;
    title: string;
    text: string;
    resolvedByPlanId?: string;
  }>;
  postgameStory?: {
    headline: string;
    summary: string;
    turningPoint?: string;
    topPerformers?: string[];
    coachingImpact?: string;
    standingsImpact?: string;
  };
};
```

Implementation should be careful with Firestore document size. If full event snapshots become too large, move detailed timeline events into a subcollection while keeping the latest score/status summary on the schedule document.

## Implementation Phases

### Phase 1: NBA Command Center V1

- Add command-center optional fields to NBA possession events.
- Add "why it happened" text for key events.
- Add turning point and importance markers.
- Upgrade Live Mode layout to show command insights and postgame story.
- Keep all controls non-mutating during the live reveal.
- Preserve compatibility with old timelines.

### Phase 2: NFL and MLB Native Live Boards

- Add football visual payloads for drive events.
- Add baseball visual payloads for plate appearance events.
- Create sport-specific board components selected by league sport.
- Group football feed by drive and baseball feed by inning/plate appearance.
- Add sport-specific postgame story facts.

### Phase 3: Background Engagement

- Add notification triggers for prep, start, clutch, and final.
- Add spoiler-safe calendar live cards.
- Store postgame recap on game history.
- Surface coaching impact and matchup lessons in scouting history.

### Phase 4: Optional Live Adjustments

Only after the passive command center is trusted:

- design small in-game adjustment windows
- add commissioner settings for live adjustment behavior
- keep missed windows fair
- add CPU solo handling
- add tests proving active watchers do not get unfair default advantage

## Testing

Domain tests:

- enriched timeline events remain backward compatible
- final score remains hidden until reveal completion
- event importance and turning point are deterministic for a seed
- NBA events with "why" text map to real possession inputs
- NFL events include valid down-distance and field position
- MLB events include valid count, outs, and base state
- no raw team IDs leak into event text, calendar cards, or postgame stories
- sport renderer selection uses league sport, not route params alone

Function tests:

- simulation writes timeline, result, live timestamps, and command-center metadata atomically
- old games without command-center fields still finalize
- notification triggers are spoiler-safe before final
- coach window text reflects stored coaching plan snapshots
- postgame story matches actual box score and timeline facts

App/source tests:

- Live Mode renders NBA, NFL, and MLB boards without sport leakage
- calendar live cards show current score without final-result spoilers
- result screen reuses stored postgame story
- command insights never expose hidden final facts early
- no mutation button appears during passive live reveal

## Non-Goals

- no manual possession control
- no arcade minigame inside the first command-center release
- no gambling-style odds presentation
- no proprietary formulas, branding, or copied competitor UI
- no required real-time attendance for competitive advantage
- no heavy 3D engine in the first version

## Risks And Mitigations

Timeline bloat:
Keep optional visual payloads compact. Move full timelines to subcollections if schedule documents approach Firestore size limits.

Notification noise:
Start with five required notification types and let users mute optional alerts later.

Perceived unfairness:
Keep Phase 1 and Phase 2 passive. If Phase 4 adds live adjustments, make them symmetric, small, logged, and commissioner-controlled.

Sport leakage:
Add source-safety tests for raw team labels, NBA terminology in NFL/MLB, and sport renderer selection.

Overbuilding visuals:
Use readable 2D boards first. The value comes from context, pacing, and story, not expensive animation.

## Acceptance Criteria

- A user can enter an NBA live game and understand the score, flow, key players, and why the game is turning.
- NFL and MLB live games feel native to their sports, not like relabeled basketball games.
- The final result is not spoiled before the live reveal reaches the end.
- Postgame recap, result screen, notifications, and game history tell the same story.
- Old completed games still render.
- Users who do not watch live remain competitively safe.

## Approval Gate

After this design is approved, write a separate implementation plan before coding. The safest first implementation slice is NBA Command Center V1 because the possession timeline and Live Mode surface already exist.
